orders: прежние MenuItem, Order, OrderItem и расчёт промокодов; добавлены флаг
акционного кэшбэка, серверная котировка бонусов, резерв и снимок бонусов в ответе заказа.
loyalty: новая предметная область, которой раньше не было. LoyaltyPolicy, Wallet,

payments: сохранён один Payment на заказ. PaymentAttempt хранит попытки,
PaymentEvent — только разрешённые факты, PaymentRefund — запросы возврата.
reviews: прежний один отзыв на заказ, статусы published/pending_moderation/hidden
совместимы с approved/pending/rejected; добавлены причина и ReviewDecision.
support: прежние беседы/сообщения/FAQ/Ollama. Контекст получает актуальные правила,
свой баланс, свои заказы и платежи, совпадения меню и промокодов. SQL/URL/изменения
заказа модель не выбирает. Небольшая FAQ ищется по словам без внешнего vector store;
изменения читаются перед каждым ответом, отдельное переиндексирование не нужно.
Frontend: существующие dashboard, профиль, отзывы, админка и история платежей
доработаны; PaymentResult добавлен как маршрут возвращения /payments/return?order=ID.
Изменения исходников перечислены в test-results/changed-files.txt.

ПРАВИЛА БОНУСОВ
Обновление 25.11.2026: для новых заказов действует JetPoints 5%/7%/10% и бонус
за второй заказ +1000. Актуальные правила и миграция: JETPOINTS_IMPLEMENTATION.txt.
Следующие абзацы описывают прежнюю программу для исторических снимков version=1.
Ранее: 1 бонус = 1 ₸; 3% базово, 7% для выбранных администратором блюд
вместо 3%; максимум 30% стоимости товаров после промокода; доставка исключена.
Бонусы не сгорают. Каждый пятый подходящий оплаченный и доставленный заказ даёт
дополнительно 500. Порог: товары после скидок и бонусов не менее 3000 ₸.
LoyaltyPolicy меняет параметры для новых заказов; существующие ставки и параметры
счётчика хранятся снимком. Предпросмотр показывает только процентное начисление:
право на бонус за пятый заказ определяется при окончательном расчёте, с учётом возвратов.
Все суммы — Decimal, точность 0.01 ₸. Максимум списания округляется ВНИЗ, чтобы не
превысить 30%. Скидка распределяется по исходной стоимости строк, бонусы — по
стоимости строк после скидки; метод наибольших остатков, равенство решает порядок строк.
Процент каждой строки округляется HALF_UP до 0.01, потом начисления суммируются.
Пример: товары 4000, скидка 400, бонусы 600, доставка 500 -> деньгами 3500;
база начисления 3000 -> 90 бонусов при 3%. Доставка не приносит бонусов.
Смешанный пример: две строки по 4000, ставки 3% и 7%, списано 2000 -> каждой
строке достаются 1000 бонусов, денежные базы по 3000 -> 90 + 210 = 300 бонусов.
Процентная награда появляется только после ОБОИХ событий: оплаты и доставки,
в любом порядке. Повторное событие не начисляет повторно. Счётчик пятых заказов
пересчитывается по времени создания подходящих заказов; возврат может перенести
дополнительную награду на следующий подходящий заказ.
Checkout резервирует бонусы; подтверждённая оплата фиксирует списание. Известный
отказ/отмена/истечение освобождает резерв. Неизвестный результат сохраняет резерв.
Изменение состава уже созданного бонусного заказа запрещено: отмените неоплаченный
заказ после проверки платежа и создайте новый. Адрес и примечание можно менять по прежним правилам.
При частичном возврате денежная сумма распределяется пропорционально остаткам
денежных товаров и доставки; затем по строкам товаров. Возвращается соответствующая
доля потраченных бонусов, процентная награда уменьшается, счётчик пересчитывается.
Это возврат доли стоимости корзины, а не выбор отдельных возвращаемых блюд.
Повторная та же накопленная сумма не создаёт операций. Если награда уже потрачена,
создаётся отдельный debt; available неотрицателен, будущие начисления гасят debt.
Полная оплата бонусами возможна только при изменении spend_percent на 100 и
нулевой доставке (или нулевом остатке доставки). Тогда внешний платёж не создаётся;
возврат такого заказа возвращает бонусы без обращения к эквайрингу.

ПРОМОКОДЫ
Существующие правила сохранены: нормализация trim+uppercase, один код, проверки
даты/ресторана/минимума/лимитов только на сервере. Предпросмотр не расходует лимит.

НАСТРОЙКА FREEDOM PAY
Официальная документация проверена 23.11.2026:
https://docs.freedompay.kz/overview-741636m0
https://docs.freedompay.kz/11620859e0
https://docs.freedompay.kz/11620963e0
https://docs.freedompay.kz/refund-payment-11621013e0
В .env.example есть шаблон, но Django читает переменные ПРОЦЕССА, не загружает
.env автоматически. Установите их в PowerShell/сервисе перед запуском:
  FREEDOMPAY_MERCHANT_ID, FREEDOMPAY_SECRET_KEY
  FREEDOMPAY_TEST_MODE=1 (сначала только тестовый режим)
  PAYMENTS_PUBLIC_URL=https://публичный-backend-домен
  PAYMENTS_RETURN_URL=http://localhost:4200/payments/return (production: HTTPS frontend)
  FREEDOMPAY_TIMEOUT=15 (не более 30 секунд)
Нужны выданные Freedom Pay тестовые merchant credentials, разрешённые KZT/эквайринг
и частичные возвраты. Публичный HTTPS POST callback: /api/payments/result.php.
Указывайте именно result.php: имя скрипта участвует в подписи. Backend подписывает
запросы и XML-ответ callback по официальному протоколу MD5; ответы провайдера также проверяются.
Callback запускает серверную сверку, проверяются сумма, KZT, ID и test/live mode.
Страница success сама ничего не подтверждает. Данные карты собирает только провайдер.
Каждая попытка имеет уникальный pg_order_id; неизвестная попытка сначала сверяется
через get_status3.php, повторная инициализация для неё не выполняется.
Промежуточный/неизвестный статус не освобождает бонусы. Просроченным считается
окончательно отвергнутый провайдером платёж после заданного init lifetime (3600 секунд).
Для задержанных уведомлений запускайте периодически (например, раз в минуту):
  py manage.py reconcile_payments
Это только сверка, она не создаёт списаний. На странице результата есть ручная проверка.
Возвраты запрашивает менеджер/администратор с явной причиной. Пустая сумма — весь
оставшийся платёж; указанная сумма — частичный возврат. Используется Idempotency-Key;
при неизвестном результате новый возврат блокируется до сверки. Внешние возвраты
в кабинете провайдера также подхватываются сверкой накопленной суммы.
Пока ключей нет, онлайн-оплата явно недоступна; можно выбрать наличные.
Локальный старый симулятор отключён; используется только под явным override в legacy-тестах.
Для production владелец должен активировать merchant account, проверить sandbox
в своём кабинете, настройки callback/HTTPS и возвратов, затем осознанно установить
FREEDOMPAY_TEST_MODE=0 и production credentials. Также требуется обычная настройка
Django production: DEBUG=False, секрет Django вне кода, ALLOWED_HOSTS, TLS, надёжная БД
и общий cache для лимитов на нескольких workers. В этой задаче production не менялся.

AI И МОДЕРАЦИЯ
Существующий провайдер Ollama; дополнительные внешние ключи не требуются для local Ollama.
  SUPPORT_OLLAMA_BASE_URL=http://127.0.0.1:11434
  SUPPORT_OLLAMA_MODEL=llama3.2:3b
  SUPPORT_OLLAMA_API_KEY= (только если endpoint требует ключ)
  SUPPORT_OLLAMA_TIMEOUT=20 (код ограничивает максимум 30 сек.)
Перед запуском должна работать Ollama с установленной моделью. FAQ редактируется в
админке Support/FAQ, обращения с историей — Support cases. Без Ollama показывается
ошибка, FAQ и обращение оператору остаются доступны. Фиксированные FAQ не выдаются за AI.
REVIEW_MODERATION_PROVIDER=local: консервативный словарно-регулярный фильтр, не
полноценная гарантия безопасности. Угрозы скрываются с причиной; сомнительные
ссылки, PII, оскорбления и дискриминационные формулировки уходят администратору.
Обычные негативные отзывы разрешены. Внешний сервис модерации не подключён:
при любом другом значении настройки отзывы остаются pending, без ложного одобрения.
Админка Reviews показывает историю решений и снимки текста; API отклонения требует причину.
После любого редактирования прежняя публикация убирается целиком до нового одобрения.
Рейтинг считается только по published; удаление и решения пересчитывают агрегаты.

ДЕМОНСТРАЦИЯ НА ЗАЩИТЕ
1. Запустите Django, Angular и Ollama. Откройте новый чат, выберите язык. Спросите
   баланс, правила бонусов, цену блюда, свой номер заказа. Смените язык и откройте
   историю. Чужой ID/номер не должен раскрывать чужие данные. Выключите Ollama:
   получите честную ошибку и покажите FAQ/создание обращения в Django admin.
2. Доведите свой заказ до delivered, оставьте отзыв от 10 символов. Негативный
   текст о холодной еде допускается. Ссылка/телефон отправят на проверку.
   В /admin/ одобрите/отклоните отзыв, покажите причину и историю. Исправьте его:
   pending и временное исчезновение из публичного рейтинга.
3. С выданными тестовыми ключами выберите online, убедитесь в надписи test mode,
   перейдите на Freedom Pay и используйте ТОЛЬКО тестовые реквизиты из кабинета/
   официальной документации. Покажите callback, verified paid и историю событий.
   Возврат до callback должен оставаться pending. Затем покажите отказ/повтор,
   частичный возврат через «Платежи» менеджера и сверку итоговой суммы.
   Без credentials этот этап BLOCKED; автоматический mock не заменяет sandbox.
4. Без внешних ключей можно честно показать расчёты через наличный заказ: заказ
   4000, доставка 0, доставьте и подтвердите получение наличных менеджером ->
   120 бонусов (3%). В следующей корзине спишите часть, покажите резерв, итог,
   последующее списание и историю профиля. Пометьте блюдо cashback_promotional
   в админке -> для нового заказа будет 7%. На пяти заказах от 3000 покажите +500.
5. Откройте FRONTEND_TEST_REPORT.md и test-results/frontend-30.json. Объясните:
   30 frontend-сценариев используют mock API; серверные гонки и гарантии проверяет
   отдельный backend-набор; реальная Ollama записана в real-ai.json.

ОГРАНИЧЕНИЯ
Реальный Freedom Pay sandbox/банк не тестировался без merchant credentials;
ни одного реального списания не выполнялось. Интеграция требует приёмки владельцем.
Текущая маленькая llama3.2:3b не даёт гарантии точности/естественности ответа:
казахские ответы при реальной проверке были неестественными и неполными.
Результаты и набор вопросов: test-results/real-ai.json, AI_SUPPORT_EVALUATION.txt.
Локальная модерация может пропустить обфускацию/контекст; полноценный внешний
сервис пока отсутствует, спорные случаи должны проверяться администратором.
Журнал профиля показывает последние 100 операций. Частичный возврат распределяется
пропорционально корзине, выбор отдельных возвращаемых позиций не реализован.
Гонки проверялись на SQLite в этой среде; PostgreSQL и многосерверная нагрузка не проверялись.
Полноценный браузерный E2E и ручной просмотр desktop/mobile не выполнялись;
DOM/component-интеграционные проверки не выдаются за ручную или банковскую проверку.
