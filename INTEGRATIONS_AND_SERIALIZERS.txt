JETFOOD — СЕРИАЛАЙЗЕРЫ И ИНТЕГРАЦИЯ BACKEND С FRONTEND

1. Общая схема приложения

JetFood разделён на две части:

- Frontend написан на Angular и работает в браузере (локально обычно
  http://localhost:4200). Он отображает страницы, принимает ввод пользователя,
  отправляет HTTP-запросы и отображает полученные данные и ошибки.
- Backend написан на Django и Django REST Framework (DRF), обычно работает на
  http://localhost:8000. Он предоставляет REST API, проверяет пользователя и
  права доступа, валидирует бизнес-правила и читает/изменяет данные в SQLite.

Данные передаются в формате JSON по HTTP. Основной префикс API — /api/. Маршруты
подключены в backend/urls.py:

- /api/auth/ — регистрация, вход, профиль, адреса, уведомления и управление
  пользователями;
- /api/orders/ — меню, заказы, статусы, назначение курьера и маршрут доставки;
- /api/restaurants/ — список ресторанов и управление ими;
- /api/payments/ — просмотр платежей, подтверждение оплаты наличными и возвраты;
- /api/analytics/ — аналитические данные;
- /api/integration/ — настройки внешних интеграций и журнал операций;
- /api/reports/ — отчёты;
- /api/search/ — поиск.

Путь конкретного запроса складывается из префикса в backend/urls.py и маршрута
приложения. Например, orders/urls.py добавляет /api/orders/<id>/status/.

2. Что такое сериалайзер и зачем он нужен

Сериалайзер DRF — это слой между JSON API и моделями/логикой Django. Он решает
две связанные задачи:

1. На входе принимает JSON, проверяет типы, обязательность и допустимые значения
   полей, затем формирует validated_data — проверенные данные, с которыми может
   безопасно работать backend.
2. На выходе преобразует модель или другой объект Python в JSON-представление,
   которое frontend может получить и отобразить.

В JetFood используются два основных варианта:

- serializers.ModelSerializer — поля обычно сопоставлены с моделью базы
  данных. Сериалайзер задаёт API-контракт, список доступных полей, read-only
  поля и дополнительные проверки.
- serializers.Serializer — набор явно объявленных полей для операций и
  запросов, которые не являются прямым отображением одной модели, например
  вход, смена статуса, параметры возврата и редактирование заказа.

Сериалайзер не заменяет всё backend-приложение. Проверка структуры и значений
данных обычно выполняется сериалайзером; проверка роли, владельца объекта,
допустимости перехода заказа и выполнение побочных действий находятся во
views.py и связанных сервисах. База данных обеспечивает постоянное хранение.

3. Как сериалайзер обрабатывает запрос

Типичный DRF-процесс выглядит так:

1. Angular отправляет запрос, например POST /api/auth/login/, с JSON-телом.
2. Django URL-конфигурация направляет его в соответствующее view.
3. View создаёт сериалайзер с входными данными: Serializer(data=request.data).
4. Вызов is_valid(raise_exception=True) запускает проверки полей и общие
   validate()-правила. Если данные некорректны, DRF возвращает клиенту HTTP 400
   и JSON с ошибками по полям или общую ошибку.
5. View проверяет аутентификацию, роль пользователя, доступ к объекту и
   бизнес-переход. Успешные проверенные значения находятся в validated_data.
6. Backend выполняет действие: сохраняет модель, запускает бизнес-логику либо
   возвращает другой объект.
7. Сериалайзер преобразует результат в JSON-ответ. HTTP-статус показывает
   общий результат: например, 200 для успешного чтения/изменения, 201 для
   создания, 400 для некорректного запроса, 401 для отсутствующей/неверной
   аутентификации и 403 для запрещённого действия.

Клиентской проверке формы нельзя доверять как защите: API можно вызвать без
страницы Angular. Поэтому важные проверки повторно выполняются на backend.

4. Примеры сериалайзеров проекта

4.1. Пользователь и аутентификация — users/serializers.py

- UserRegistrationSerializer принимает имя пользователя, email, пароль и
  телефон. Пароль имеет write_only=True, поэтому его можно отправить при
  регистрации, но он не попадёт в JSON-ответ. Минимальная длина — 8 символов.
  Email проверяется на уникальность без учёта регистра. Публичная регистрация
  не позволяет назначить себе привилегированную роль: поле role только для
  чтения, а create() удаляет переданную роль перед созданием пользователя.
- AdminUserCreateSerializer расширяет регистрацию для административного
  сценария и разрешает назначить роль; доступ к самому административному
  endpoint дополнительно ограничивается view.
- LoginSerializer проверяет username и password через Django authenticate().
  При успехе он добавляет пользователя в validated_data, а LoginView возвращает
  токен и безопасное представление пользователя через UserSerializer.
- UserSerializer не включает пароль и определяет, какие пользовательские поля
  доступны в API.
- ChangePasswordSerializer и AccountDeletionSerializer проверяют поля для
  отдельных операций. Само право на операцию и проверка текущего пароля
  выполняются во view.
- DeliveryAddressSerializer и NotificationSerializer задают JSON-формат
  адресов доставки и уведомлений.

4.2. Заказы, меню и доставка — orders/serializers.py

- MenuItemSerializer выдаёт данные блюда и связанное имя ресторана. Поле
  restaurant_name берётся из restaurant.name и доступно только для чтения;
  рейтинг тоже read-only. Цена ограничена положительным значением.
- OrderItemSerializer разделяет идентификатор блюда на входе и данные для
  показа. item_id — write-only ссылка на активное блюдо, item_name и
  price_per_item — read-only снимки для ответа, quantity должна быть не меньше
  одного. menu_item_id возвращается только для чтения и допускает null.
- OrderSerializer принимает вложенный список items и данные адреса/оплаты, а
  возвращает сведения о заказе, его клиенте, курьере, статусе, времени и
  позициях. Статус, итоговая сумма, номер заказа и назначенный курьер
  read-only: клиент не должен сам назначить курьера или подменить сумму.
  Вложенный create() создаёт заказ и строки OrderItem, связывая каждую строку
  с существующим блюдом. Общая сумма, номер и начальный статус задаются во
  view, а не берутся как достоверные от браузера.
- OrderStatusUpdateSerializer принимает статус из допустимого набора. Он
  проверяет, что статус распознан, но допустимость конкретного перехода
  (например, готов к выдаче → доставка) дополнительно проверяет
  orders/views.py.
- CourierAssignmentSerializer проверяет, что переданный delivery_person_id
  соответствует активной учётной записи курьера.
- OrderModificationSerializer разрешает изменять только разрешённые поля,
  проверяет состав блюд и не допускает пустое изменение.
- DeliveryRouteInputSerializer проверяет адрес, географические границы
  координат, диапазоны расстояния и длительности и их взаимную обязательность.
  DeliveryRouteSerializer формирует ответ с названием получателя, ссылкой на
  OpenStreetMap и метаданными, часть которых только для чтения.

4.3. Рестораны — restaurants/serializers.py

RestaurantSerializer сопоставляет JSON с моделью ресторана. Он проверяет, что
рабочие дни являются числами от 0 (понедельник) до 6 (воскресенье), не
повторяются, а время закрытия позже времени открытия. Право создавать,
изменять и удалять ресторан проверяется отдельно в restaurants/views.py.

4.4. Платежи — payments/serializers.py

PaymentSerializer возвращает данные платежа, включая номер заказа и имя
клиента, получаемые из связанных моделей. Все поля этого сериалайзера
read-only: изменение статуса платежа делается только разрешёнными backend
операциями. RefundSerializer проверяет причину возврата; право и возможность
возврата проверяются во view.

4.5. Интеграции, аналитика и отчёты

- ExternalIntegrationSerializer позволяет отправить ключ при создании или
  обновлении, но api_key имеет write_only=True и никогда не возвращается
  браузеру. Вместо самого секрета ответ содержит api_key_present — только
  признак, настроен ли ключ. Это предотвращает случайное раскрытие ключа
  через список или карточку интеграции.
- IntegrationLogSerializer, AnalyticsEventSerializer,
  SystemMetricSerializer, PerformanceReportSerializer, ReportSerializer и
  ReportScheduleSerializer задают формы JSON для журналов, аналитики и отчётов.
  Вычисляемые связанные поля, например integration_name, username и
  generated_by_name, формируются из связанных объектов и обычно read-only.

5. Связь между backend и frontend

5.1. Frontend API-сервисы

Angular-компонент отвечает за интерфейс: форму, таблицу, карту или кнопку.
Для HTTP-запросов он использует отдельный сервис с HttpClient. Сервис
централизует адрес endpoint, типы входных/выходных данных и методы операций.
Например:

- frontend/src/app/auth.ts — регистрация, вход, выход, получение профиля и
  хранение локального состояния текущей сессии;
- frontend/src/app/orders.ts — запрос списка и детализации заказов, изменение
  статуса, назначение курьера, загрузка/сохранение маршрута;
- frontend/src/app/menu.ts — список, создание и изменение блюд;
- frontend/src/app/restaurants.ts — операции со списком ресторанов;
- frontend/src/app/payments.ts — список платежей, подтверждение наличной оплаты
  и запрос возврата;
- frontend/src/app/integration.ts — CRUD интеграций, проверка/синхронизация и
  загрузка журналов.

TypeScript-интерфейсы, например OrderRecord, DeliveryRoute и PaymentRecord,
описывают ожидаемые формы данных и помогают редактору и компилятору находить
несовпадения в коде Angular. Это не runtime-проверка доверенного ответа:
реальную валидацию и авторизацию всё равно выполняет backend.

5.2. Авторизация запроса

При входе POST /api/auth/login/ Angular получает от backend токен и сведения
пользователя. Токен сохраняется в localStorage. authInterceptor подключён в
frontend/src/app/app.config.ts: для запросов к API он добавляет заголовок
Authorization: Token <токен>. Backend DRF TokenAuthentication проверяет токен и
передаёт аутентифицированного пользователя в request.user.

Interceptor ограничивает время ожидания HTTP-ответа 15 секундами. При ответе
401 он очищает локальные данные сессии и направляет пользователя на страницу
входа. Ошибки 400, 403 и сетевые ошибки передаются вызывающему компоненту, где
страница может показать соответствующее сообщение.

Некоторые сервисы проекта задают Authorization явно, другие используют
глобальный interceptor. В обоих случаях запрос должен адресоваться API, а не
внешнему сервису, чтобы заголовок токена не был отправлен не по назначению.

5.3. Форматы списка

DRF по умолчанию настроен на пагинацию по 20 элементов: список может прийти как
массив или как объект с полем results и метаданными пагинации. Утилита
frontend/src/app/shared/api-list.ts приводит оба этих формата к массиву для
списковых экранов. Для отдельных endpoint пагинация может быть отключена.

5.4. Пример: создание заказа

1. Компонент корзины собирает адрес доставки, способ оплаты и список строк
   заказа с item_id и quantity.
2. Angular Orders API-сервис отправляет POST /api/orders/ с JSON и токеном.
3. DRF аутентифицирует пользователя, OrderSerializer проверяет вложенные поля
   и находит доступные блюда.
4. OrderListCreateView дополнительно проверяет ограничения числа ожидающих
   заказов, количество блюд, итоговую сумму и планируемое время доставки.
   Сумму считает backend по текущим ценам блюд; клиент не является источником
   истины для общей стоимости.
5. В транзакции создаются заказ, строки заказа и запись платежа, запускается
   уведомление о создании заказа.
6. Backend возвращает сериализованный заказ; Angular обновляет состояние
   страницы и показывает новый заказ или ошибку.

5.5. Пример: маршрут доставки

1. Angular-компонент карты получает координаты A и B и рассчитывает маршрут
   через OSRM; затем пользователь сохраняет адрес, координаты, расстояние и
   длительность через PUT /api/orders/<id>/route/.
2. DeliveryRouteInputSerializer проверяет диапазоны и целостность полей;
   delivery_route view проверяет, что пользователь — администратор, менеджер
   или назначенный этому заказу курьер.
3. Backend сохраняет маршрут. GET того же endpoint возвращает
   DeliveryRouteSerializer в JSON.
4. Перед началом доставки backend требует маршрут с координатами и метриками.
   При успешном переходе в delivering он сам записывает delivery_started_at и
   estimated_arrival_time. Angular использует эти серверные значения для ETA
   и таймера.

6. Права доступа и проверки

Аутентификация отвечает на вопрос «кто отправил запрос?». Авторизация отвечает
на вопрос «может ли этот пользователь выполнить это действие с этим объектом?».
Наличие токена само по себе не даёт прав администратора.

DRF permission_classes, фильтрация queryset во views и проверки ролей
ограничивают доступ к данным. Например, клиент получает свои заказы, курьер —
назначенные ему, менеджер/администратор имеют расширенные операции. Сериалайзер
может дополнительно ограничить допустимую ссылку на объект (например,
назначаемый курьер должен быть активным пользователем с ролью delivery).

Важные правила проекта распределены между слоями:

- формат и поля JSON — сериалайзер;
- доступ к endpoint и объекту — permission_classes и queryset во view;
- бизнес-переход и побочные действия — view/сервисы;
- сохранение и связи — модели и база данных;
- отображение и пользовательский сценарий — Angular-компоненты.

7. Ошибки и их обработка

- HTTP 400 — неправильный JSON или нарушение валидации/бизнес-правила. DRF
  обычно возвращает объект с detail либо сообщениями по именам полей.
- HTTP 401 — пользователь не вошёл или токен не принят; interceptor завершает
  локальную сессию и открывает страницу входа.
- HTTP 403 — пользователь вошёл, но действие ему запрещено.
- HTTP 404 — объект или endpoint не найден либо скрыт от текущего пользователя.
- HTTP 5xx/сетевая ошибка — сбой backend или соединения.

Angular-сервисы возвращают Observable. Компонент подписывается на результат:
при успехе обновляет данные, при ошибке показывает уведомление/сообщение, а
пока запрос выполняется, обычно блокирует повторное нажатие. Детали ответа
не следует считать успешными только потому, что браузер отправил запрос:
успех определяется ответом сервера.

8. Локальная настройка связи

Для текущего локального запуска:

- Angular: http://localhost:4200;
- Django API: http://localhost:8000;
- CORS на backend разрешает frontend-источники
  http://localhost:4200 и http://127.0.0.1:4200;
- общий корень endpoint задаётся в сервисах Angular и сейчас указывает на
  http://localhost:8000/api/.

При размещении на сервере необходимо настроить API URL для окружения, список
разрешённых CORS origins, HTTPS, секреты и безопасное хранение конфигурации.
Нельзя использовать демонстрационные настройки Django DEBUG=True и встроенный
development SECRET_KEY в публичной production-системе.

9. Внешние интеграции и границы текущей реализации

Модуль integration хранит настройки внешних интеграций и журнал операций.
Однако endpoints test и sync сейчас имитируют операции и записывают события в
локальный журнал; они не подключаются к произвольному api_endpoint и не
выполняют реальный обмен данными с платёжным провайдером или сервисом
уведомлений. Онлайн-оплата в проекте также является демонстрационной
симуляцией, а не банковской транзакцией.

Для реальной интеграции потребуются конкретный провайдер, его API-клиент,
безопасное хранение и ротация ключей, обработка сетевых ошибок и повторов,
проверка подписей/webhook и тесты против тестовой среды поставщика.

10. Основные файлы

Backend:
- backend/urls.py — подключение API-маршрутов приложений;
- backend/settings.py — DRF, аутентификация, пагинация и CORS;
- users/serializers.py и users/views.py — пользователи и аутентификация;
- orders/serializers.py, orders/views.py и orders/urls.py — меню, заказы и
  доставка;
- restaurants/serializers.py и restaurants/views.py — рестораны;
- payments/serializers.py и payments/views.py — платежи и возвраты;
- integration/serializers.py и integration/views.py — интеграции и логи;
- analytics/serializers.py, reports/serializers.py — аналитика и отчёты.

Frontend:
- frontend/src/app/app.config.ts — подключение HTTP-клиента и interceptor;
- frontend/src/app/auth.interceptor.ts — токен, таймаут и реакция на 401;
- frontend/src/app/auth.ts — операции входа и пользовательская сессия;
- frontend/src/app/orders.ts, menu.ts, restaurants.ts, payments.ts,
  integration.ts — Angular API-сервисы и типы данных;
- frontend/src/app/shared/api-list.ts — нормализация списковых ответов;
- frontend/src/app/orders/ и другие каталоги компонентов — формы, страницы и
  действия интерфейса.

11. Проверки

Из корневой папки JetFood:
  python manage.py test

Из папки frontend:
  npm test -- --watch=false
  npm run build

Тесты backend проверяют валидацию, права доступа, переходы состояния и ответы
API. Тесты Angular проверяют сервисы и сценарии интерфейса. Production-сборка
проверяет компиляцию frontend и шаблонов; она сама по себе не доказывает, что
каждый endpoint доступен на развёрнутом сервере, поэтому нужен также сквозной
тест с запущенными frontend и backend.
