JETFOOD — ОПИСАНИЕ РАЗДЕЛОВ И ТАБЛИЦА ТЕСТИРОВАНИЯ
Дата проверки: 09.11.2026

1. TESTING — ТЕСТИРОВАНИЕ
Автоматические тесты проверяют backend API и Angular-интерфейс.

Backend-тесты:
- orders/tests.py — создание заказов, серверный расчет цены, лимиты,
  доступ к заказам, последовательность статусов, управление маршрутами,
  уведомления, подтверждение получения и сводка.
- users/tests.py — вход, регистрация, права администратора и роли.
- analytics/tests.py — системные метрики и права на аналитику.
- reports/tests.py — отчеты, полный конечный день периода, скачивание
  сводки и расписания.
- integration/tests.py — создание и проверка/синхронизация интеграций.
- payments/tests.py — симуляция онлайн-платежа, наличные, история и возвраты.
- backend/tests.py — глобальный поиск, включая разграничение заказов
  и поиск блюд на русском и английском.

Frontend-тесты находятся рядом с компонентами в файлах *.spec.ts.
Они проверяют интерфейс, фильтрацию меню и корзину, статусы заказов,
переключение языка, поиск и состояния ошибок.

Команды запуска из папки проекта:
  python manage.py test
  Set-Location frontend; npm test -- --watch=false
  Set-Location frontend; npm run build

2. ANALYTICS — АНАЛИТИКА
Где находится:
- Интерфейс: frontend/src/app/analytics/analytics.html и analytics.ts
- API: analytics/views.py, маршрут /api/analytics/analysis/
- Доступ к странице: frontend/src/app/app.routes.ts

Что показывает API системной аналитики:
- число заказов и сумму покупок по клиентам;
- время доставки завершенных заказов;
- активных пользователей за последние 30 дней;
- выручку и количество доставок за последние 7 дней;
- предложения по ролям для пользователей с большим числом заказов.

Доступ к аналитике разрешен ролям admin, manager и analyst. Предложения
по ролям являются аналитической рекомендацией. Их применение вынесено
в отдельный API-маршрут и требует роль admin.

3. REPORT — ОТЧЕТЫ
Где находится:
- Интерфейс: frontend/src/app/reports/reports.html и reports.ts
- API и генерация: reports/views.py
- Маршруты: reports/urls.py, общий префикс /api/reports/

Отчеты можно создавать по продажам, доставке, клиентам и эффективности.
Данные продаж считают только доставленные заказы; для отчетов по датам
учитывается весь конечный день. Экран показывает состояние отчетов.
Сводка, полученная от API, скачивается frontend как JSON-файл.

Важно: несмотря на возможность указать PDF/Excel/CSV в формате отчета,
полноценные PDF/Excel/CSV-файлы сейчас backend не формирует. Текущая
реализованная загрузка в интерфейсе — JSON-сводка.

4. SUM OF ORDERS — СВОДКА ЗАКАЗОВ И ВЫРУЧКИ
Где находится:
- Расчет на backend: orders/views.py, функция order_summary
- API: GET /api/orders/summary/
- Фильтр периода: orders/date_filters.py
- Клиентский метод: frontend/src/app/orders.ts, getOrderSummary()

Сводка возвращает количество заказов, сумму total_amount и количество
заказов по каждому статусу за выбранный период. Разрешена admin,
manager и analyst. Важно: метод API-клиента существует, но отдельный
экран пока не вызывает этот endpoint напрямую. Суммарные данные также
формируются в отчетах о продажах и могут быть скачаны как JSON.

5. INTEGRATION — ИНТЕГРАЦИИ
Где находится:
- Интерфейс: frontend/src/app/integration/integration.html и integration.ts
- API: integration/views.py
- Маршруты: integration/urls.py, префикс /api/integration/
- Модели и журнал: integration/models.py

Раздел показывает внешние интеграции, их тип/статус и время последней
синхронизации. Доступны создание, просмотр, изменение, удаление,
тестирование и синхронизация с ограничениями по ролям. Тестирование
создает запись журнала. Синхронизация создает журнал и обновляет
last_sync.

Важно: фактический сетевой запрос к платежному, картографическому или
другому внешнему провайдеру пока не выполняется. Проверка интеграции
имитируется записью журнала, синхронизация обновляет локальные данные.

6. RESTAURANTS — РЕСТОРАНЫ И ИХ МЕНЮ
Где находится:
- Интерфейс: frontend/src/app/restaurants/
- API и модель ресторанов: restaurants/views.py, restaurants/models.py
- API меню: orders/views.py, orders/models.py
- Маршруты: /api/restaurants/ и /api/orders/menu/

Клиенты могут просматривать активные рестораны, их адрес, часы работы
и меню. Администраторы и менеджеры могут регистрировать, редактировать
и удалять рестораны, указывать рабочие дни и время открытия/закрытия,
а также добавлять, изменять, удалять и временно отключать блюда.
Неактивные рестораны и блюда не показываются клиентам. Управление
защищено проверками ролей на backend.

Старые блюда без ресторана сохранены и продолжают работать. У ресторанов
нет отдельной роли владельца: управлять ими могут admin и manager.

8. CUSTOMER MANAGEMENT — ПРОФИЛЬ И АДРЕСА
Страница frontend/src/app/profile/ даёт клиенту редактировать профиль,
управлять несколькими адресами доставки, выбирать основной адрес и менять
пароль после проверки текущего. Основной адрес можно выбрать в корзине.
Удаление аккаунта требует пароль: учётная запись деактивируется, контактные
данные и сохранённые адреса удаляются, завершённые заказы сохраняются без
адреса доставки и инструкций. Пока есть активные заказы, удаление запрещено.
API находится в users/views.py; модель адреса — users/models.py.

9. ORDER EDITING — ФИЛЬТР ЦЕНЫ И ИЗМЕНЕНИЕ ЗАКАЗА
Панель каталога позволяет задать минимальную и максимальную цену.
Клиент может менять состав, адрес доставки и комментарий своего заказа
только до подтверждения (статус pending). API перепроверяет владение
заказом и статус, ограничивает количество блюд и пересчитывает сумму
по актуальным ценам меню.
Где: frontend/src/app/dashboard/, frontend/src/app/orders/,
orders/views.py и orders/serializers.py.

10. PAYMENT MANAGEMENT — ОПЛАТА И ВОЗВРАТЫ
При создании заказа клиент выбирает онлайн-симуляцию или наличные.
Онлайн-симуляция сразу создаёт успешный платеж с SIM-транзакцией; реальные
банковские данные и запросы не используются. Наличные ожидают подтверждения
после доставки. При отмене оплаченного онлайн-заказа создаётся запрос
возврата; admin/manager может оформить возврат с причиной. Клиенты видят
только свою историю, admin/manager — все платежи.
Где: payments/, frontend/src/app/payment-history/, backend/urls.py.

Примечание к сборке: Angular сообщает CSS-предупреждения бюджета для
frontend/src/app/dashboard/dashboard.css и landing/landing.css. Сборка
завершается успешно; предупреждения не блокируют приложение.

11. DELIVERY MANAGEMENT — МАРШРУТ И ПОЛУЧЕНИЕ ЗАКАЗА
Назначенный курьер или admin/manager выбирает точки A и B на карте Leaflet
с подложкой OpenStreetMap. Маршрут, расстояние и ориентировочное время
получаются от публичного OSRM роутера, координаты сохраняются backend в
DeliveryRoute, клиент может увидеть карту и открыть маршрут на
OpenStreetMap. GPS-трекинга и оценки времени с учётом пробок нет.
После статуса delivered клиент может отдельно подтвердить получение;
backend сохраняет время подтверждения и проверяет владельца заказа.
Модель DeliveryRoute, API и миграция находятся в orders/; интерфейс —
frontend/src/app/orders/.

12. ROLE DEMO USERS, NOTIFICATIONS, AND SERIALIZER CONTRACTS
Команда `python manage.py create_demo_roles` создаёт demo_admin,
demo_manager и demo_courier и выводит случайные пароли только при создании.
Статусы заказов и назначение курьеров создают персональные in-app
уведомления; экран обновляет их каждые 30 секунд.
Интеграционный API поддерживает UI CRUD и журнал; api_key принимается
только на запись и не возвращается клиенту. Интеграционный test/sync и
online payment остаются локальными симуляциями.
