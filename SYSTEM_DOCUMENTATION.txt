System Analysis Implementation (system_analysis() function):
-----------------------------------------------------------
Performs comprehensive analysis of system data:

1. Order Volume Analysis:
   - Groups orders by customer
   - Counts total orders per customer
   - Calculates total spent per customer
   - Returns top 10 customers by order volume

   - Calculates daily revenue and daily order count
   - Returns chronological trend data

-----------------------------------------------------------
Allows Admin to apply suggested role changes:

2. Validates each target user exists
3. Validates new role is valid (from ROLE_CHOICES)
4. Updates user.role field
5. Returns list of successfully applied updates

Access Control:
- Admin only
- Uses validate_role_access(['admin'])

Example Workflow:
1. Manager calls GET /api/analytics/system-analysis/
2. System returns analysis with role suggestions
3. Admin reviews suggestions
4. Admin calls POST /api/analytics/apply-role-updates/ with updates

Location: C:\Users\tald1\Desktop\Food_delivery\users\constraints.py

Business Constraints Class:
---------------------------
Defines all system-wide business rules:

Order Constraints:
- MIN_ORDER_AMOUNT: $10.00 (minimum order value)
- MAX_ORDER_AMOUNT: $10,000.00 (maximum order value)
- MAX_ITEMS_PER_ORDER: 50 items per order

Delivery Constraints:
- MAX_DELIVERY_TIME_HOURS: 4 hours maximum delivery time
- MIN_DELIVERY_TIME_MINUTES: 30 minutes minimum delivery time

User Constraints:
- MIN_PASSWORD_LENGTH: 8 characters minimum
- MAX_PENDING_ORDERS_PER_USER: 5 pending orders maximum

System Constraints:
- MAX_ORDERS_PER_HOUR: 100 orders per hour system limit
- MAX_CONCURRENT_USERS: 500 concurrent users maximum

Validation Functions:
---------------------
1. validate_order_amount(amount):
   - Checks order is between $10 and $10,000
   - Raises ValidationError if out of range
   - Used in orders/views.py when creating orders

2. validate_delivery_time(estimated_time):
   - Ensures delivery time is between 30 min and 4 hours from now
   - Prevents unrealistic delivery promises
   - Used in orders/views.py

3. validate_user_pending_orders(user):
   - Counts user's pending/confirmed/preparing/delivering orders
   - Blocks new orders if user has 5+ pending orders
   - Prevents order spam
   - Used in orders/views.py

4. validate_role_access(user, required_roles):
   - Checks if user.role is in required_roles list
   - Raises ValidationError if access denied
   - Used throughout the system for role-based access control
   - Example: validate_role_access(user, ['admin', 'manager'])

Constraint Enforcement Points:
- Order creation: validates amount, delivery time, pending order count
- Report creation: validates role (admin/manager/analyst only)
- Integration management: validates role (admin/manager only)
- Analytics access: validates role for viewing sensitive data
- Role updates: validates admin role only

User Model (users/models.py):
-------------------------------
- Extends Django's AbstractUser
- Fields:
  * role: One of [admin, manager, analyst, delivery, customer]
  * phone: Phone number with regex validation
  * address: Text field for address
  * created_at, updated_at: Timestamps
- Custom database table: auth_user
- String representation: "{username} ({role})"

Role Hierarchy:
----------------
1. admin: Full system access, can manage all users and settings
2. manager: Can manage orders, reports, integrations, view analytics
3. analyst: Can view analytics and reports (read-only)
4. delivery: Can manage assigned orders, update delivery status
5. customer: Can create orders, view own orders, cancel pending orders

Authentication Methods:
-----------------------
1. Token Authentication (Primary):
   - REST Framework Token Authentication
   - Token generated on login
   - Token stored in localStorage in frontend
   - Sent in Authorization header: "Token {token_key}"

2. Session Authentication (Secondary):
   - Django session-based authentication
   - Used for admin panel

Authentication Endpoints (users/views.py):
-------------------------------------------
1. RegisterView (POST /api/auth/register/):
   - Public endpoint (no authentication required)
   - Creates new user with UserRegistrationSerializer
   - Default role: 'customer'
   - Validates phone number format

2. LoginView (POST /api/auth/login/):
   - Public endpoint
   - Accepts username and password
   - Returns token and user data
   - Token created if doesn't exist

3. LogoutView (POST /api/auth/logout/):
   - Requires authentication
   - Deletes user's auth token
   - Calls Django logout()

4. ChangePasswordView (POST /api/auth/change-password/):
   - Requires authentication
   - Validates old password
   - Updates to new password
   - Uses Django's set_password() method (hashes automatically)

5. UserProfileView (GET/PUT /api/auth/profile/):
   - Requires authentication
   - User can only view/update their own profile

6. UserListView (GET /api/auth/users/):
   - Requires authentication
   - Admin sees all users
   - Manager sees delivery and customer users
   - Other roles see only themselves

7. UserDetailView (GET/PUT/DELETE /api/auth/users/{id}/):
   - Requires authentication
   - Users can update their own profile
   - Admin can update/delete any user
   - Role changes require admin approval

8. update_user_role (POST /api/auth/users/{id}/role/):
   - Admin only
   - Updates user role
   - Validates role is in ROLE_CHOICES

Access Control Implementation:
------------------------------
Role-based access is enforced throughout the system:

1. In Views (using validate_role_access):
   ```python
   validate_role_access(user, ['admin', 'manager'])
   ```

2. In QuerySets (filtering by role):
   ```python
   if user.role == 'admin':
       return Order.objects.all()
   elif user.role == 'manager':
       return Order.objects.all()
   elif user.role == 'delivery':
       return Order.objects.filter(delivery_person=user)
   else:
       return Order.objects.filter(customer=user)
   ```

3. In Actions (role-specific permissions):
   - Customers can only cancel pending orders
   - Delivery persons can only update to 'delivering' or 'delivered'
   - Admin/Manager have full access

6. PASSWORD PROTECTION IN BACKEND
================================================================================

Location: C:\Users\tald1\Desktop\Food_delivery\users\

Password Storage:
-----------------
- Uses Django's built-in password hashing system
- Passwords are never stored in plain text
- Django uses PBKDF2 algorithm with SHA256 hash by default
- Salt is automatically generated and stored with the hash
- Hash stored in auth_user.password field

Password Change Implementation (users/views.py, lines 53-63):
-------------------------------------------------------------
ChangePasswordView endpoint:
- Requires authentication (user must be logged in)
- Accepts: old_password, new_password
- Validates old password using Django's check_password()
- Updates password using set_password() method
- set_password() automatically:
  * Generates new salt
  * Hashes the new password
  * Stores the hash in database

Code:
```python
class ChangePasswordView(generics.GenericAPIView):
    permission_classes = [permissions.IsAuthenticated]
    serializer_class = ChangePasswordSerializer
    
    def post(self, request):
        serializer = self.get_serializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        user = request.user
        user.set_password(serializer.validated_data['new_password'])
        user.save()
        return Response({'message': 'Password changed successfully'})
```

Password Validation (Django Built-in):
-------------------------------------
In backend/settings.py (lines 95-108):
1. UserAttributeSimilarityValidator:
   - Prevents passwords too similar to user attributes (username, email, etc.)

2. MinimumLengthValidator:
   - Enforces minimum password length (default 8 characters)
   - Configured in users/constraints.py as MIN_PASSWORD_LENGTH = 8

3. CommonPasswordValidator:
   - Prevents use of common/weak passwords (e.g., "password", "123456")

4. NumericPasswordValidator:
   - Prevents purely numeric passwords

Additional Password Constraints (users/constraints.py):
-------------------------------------------------------
- MIN_PASSWORD_LENGTH: 8 characters minimum
- Enforced through Django's MinimumLengthValidator

Password Requirements:
-----------------------
1. Minimum 8 characters
2. Not similar to username or email
3. Not a common password
4. Not purely numeric
5. Old password must be correct for password change

Registration Password Handling (users/serializers.py):
-----------------------------------------------------
UserRegistrationSerializer:
- Uses Django's create_user() method
- Automatically hashes password
- Stores hash in database
- Never exposes plain text password

Login Password Verification (users/serializers.py):
--------------------------------------------------
LoginSerializer:
- Uses Django's authenticate() function
- authenticate() automatically:
  * Retrieves password hash from database
  * Hashes provided password with stored salt
  * Compares hashes
  * Returns user if match, None if no match

Password Security Best Practices Implemented:
---------------------------------------------
1. ✓ Passwords never stored in plain text
2. ✓ Strong hashing algorithm (PBKDF2 with SHA256)
3. ✓ Unique salt for each password
4. ✓ Password validation on registration
5. ✓ Old password verification on change
6. ✓ Minimum length requirement (8 characters)
7. ✓ Prevention of common passwords
8. ✓ Prevention of passwords similar to user data
9. ✓ Tokens used for API authentication (separate from passwords)
10. ✓ Token deletion on logout (invalidates session)

Password Recovery (Not Implemented):
-------------------------------------
- Current system does not have password reset functionality
- Would require implementing:
  * Password reset token generation
  * Email sending configuration
  * Reset token validation
  * Password reset endpoint

Security Notes:
---------------
- SECRET_KEY in settings.py should be environment variable in production
- Current SECRET_KEY is for development only
- Tokens are separate from passwords and used for API authentication
- Token authentication stateless (no server-side session storage)
- Password change invalidates session but does not invalidate tokens (admin can delete tokens if needed)
